# Kanji 5 v1.9 Roadmap

# v1.9 Release-Closeout Verification

- Package version is `1.9.0`.
- P0–P6 are merged on `main`.
- P7 documentation/release gates are implemented.
- Active service-worker shell cache is `v69`.
- v2 view-model contracts and the runtime boundary are documented and test-backed.

## Product goal

Make the current five-skill learning engine substantially smarter, more reliable, measurable, and maintainable before v2 introduces the major visual/UI redesign.

v1.9 is the **last pre-v2 learning-engine release**. It should improve the intelligence and correctness of the existing product without changing its visual identity, introducing a new visual navigation model, or replacing FSRS.

The outcome of v1.9 should be a stable educational core that v2 can consume through clean interfaces rather than requiring v2 to rewrite learning logic.

---

## v1.9 guiding principles

1. **Intelligence before cosmetics.** Improve selection, grading, learner modeling, recovery, content quality, and evaluation before spending engineering scope on visual redesign.
2. **Five skills remain the product model.** Meaning, Reading, Production, Vocabulary, and Context remain the supported recall attributes. Do not add a sixth learner-facing exercise mode in v1.9.
3. **FSRS remains the card scheduler.** Attribute-level intelligence may influence what to practice, but it must not become a second card-scheduling system.
4. **Deterministic cores stay pure.** Planning, grading, learner modeling, evaluation, and tuning must remain testable without DOM, browser storage, network, or Supabase.
5. **Learning outcomes are evidence.** The system should distinguish wrong, unknown, correct, recovery, and repeated failure rather than collapsing everything into one accuracy number.
6. **No hidden auto-tuning.** Evaluation may recommend changes, but it must not silently rewrite learner state or planner parameters.
7. **v2-safe interfaces.** v1.9 may improve the current UI only where necessary to expose learning information, but business logic must remain decoupled from presentation so v2 can replace the visual layer later.
8. **Offline-first remains mandatory.** Core grading, planning, learner-model calculations, and recovery must continue working without remote services.

# Priority order

## P0 — Grading & Outcome Quality 2.0 ✅

### Goal
Make the five learning modes produce reliable, educationally meaningful, versioned outcomes before making the planner more sophisticated.

### Scope

- Audit all five canonical graders: Meaning, Reading, Production, Vocabulary, Context.
- Define one normalized outcome contract for all educational modes.
- Separate at minimum:
  - `correct`
  - `wrong`
  - `unknown`
  - `empty`
  - `invalid` / unusable input where applicable
- Preserve mode-specific grading rules while standardizing the output shape.
- Add grader contract/version metadata so future grading changes can be distinguished from historical outcomes.
- Review normalization rules for Unicode, Japanese script variants, whitespace, punctuation, casing where relevant, and canonical/acceptable answers.
- Allow explicit, deterministic acceptable-answer sets where educationally justified; do not introduce remote or generative grading.
- Ensure every accepted alternative is intentionally defined and test-backed.
- Record the answer evidence needed by later evaluation without storing unnecessary raw sensitive input.

### Acceptance criteria

- All five modes conform to a shared outcome contract.
- Each mode has explicit deterministic grading rules and negative cases.
- `unknown` is not silently converted into `wrong`.
- Grader behavior is versioned.
- Contract tests cover canonical, valid alternative, wrong, empty, and malformed cases where applicable.
- No grader requires network access.

### Required tests

- Unit tests for every mode.
- Cross-mode outcome-contract tests.
- Regression tests for known v1.8 behavior.
- Browser tests proving the learner-facing outcome reaches session feedback and persistence correctly.

## P1 — Learner Model 2.0 ✅

### Goal
Turn historical session outcomes into a richer but deterministic model of what the learner knows, what is weak, what is unstable, and what is recovering.

### Scope

Build on the existing long-term skill profile rather than replacing it.

### Required signals

For each Kanji and each supported attribute where evidence exists, derive:

- lifetime attempts
- lifetime accuracy
- recent accuracy
- recent attempt count
- current error streak
- current success streak
- last attempt timestamp / recency
- momentum / trend
- recovery count or recovery strength
- repeated-failure signal
- confidence / evidence strength
- mastery state
- uncertainty state

### Knowledge states

Use deterministic states such as:

- `unseen`
- `introduced`
- `learning`
- `weak`
- `recovering`
- `stable`
- `mastered`

The exact thresholds must be centralized and versioned rather than scattered throughout UI code.

### Kanji-level vs attribute-level

- Keep **card-level learning state** and FSRS state authoritative for card scheduling.
- Keep **attribute-level state** authoritative for choosing what kind of recall to practice.
- Allow a Kanji to be strong in Reading but weak in Production without forcing one combined score.

### Acceptance criteria

- Learner-model calculations are deterministic and pure.
- Historical session data can be projected into the model without mutating history.
- Attribute-level weakness is queryable per Kanji.
- Evidence strength prevents overreacting to one or two attempts.
- Model versioning is explicit.
- Existing v1.6/v1.7/v1.8 consumers remain backward-compatible.

### Required tests

- Golden fixtures for representative learner histories.
- Threshold-boundary tests.
- Empty/new-user tests.
- Sparse-evidence tests.
- Recovery and repeated-failure fixtures.
- Migration compatibility tests.

## P2 — Adaptive Planner 3.0 ✅

### Goal
Use the richer learner model to select the most educationally useful next recall task while remaining deterministic, explainable, and bounded.

### Planner inputs

- due/new/review status from existing scheduler/session state
- attribute-level mastery
- recent accuracy
- error streak
- recovery strength
- recency
- uncertainty/evidence strength
- recent modes already practiced in the same session
- session budget
- content availability

### Planner behavior

The planner should explicitly distinguish at least:

- **repair:** a recent failure needs another supported attempt
- **reinforce:** a weak but known attribute needs strengthening
- **recover:** a previously weak attribute is improving and needs confirmation
- **maintain:** a mastered/stable attribute only needs occasional exposure
- **explore:** unseen or under-evidenced attribute needs first evidence

### Anti-repetition rules

- Do not repeatedly select the same attribute for a Kanji without evidence-based reason.
- Avoid immediate mode repetition when another meaningful supported mode is available.
- Do not starve a weak attribute merely because another attribute has more total attempts.
- Do not create an infinite retry loop after failure.

### Difficulty targeting

Introduce deterministic difficulty bands based on existing learner evidence rather than arbitrary UI labels.

Examples:

- low difficulty: stable recall / high confidence
- medium difficulty: weak or recently missed
- high difficulty: repeated error / long-standing instability

The planner may choose among existing modes to target these bands; it must not create a new exercise type solely to represent difficulty.

### Adaptive budget

Allow the planner to choose a bounded number of attribute recalls per session while respecting the existing session lifecycle.

### Acceptance criteria

- Planner remains a pure function.
- Every selected mode is supported and test-backed.
- Selection is explainable from explicit signals.
- Same input snapshot produces the same plan.
- Session feedback can rebalance only remaining work.
- FSRS due scheduling is never overwritten by the attribute planner.
- No mode can monopolize an entire session unless the configured evidence rules explicitly justify it.

### Required tests

- Planner score fixtures.
- Tie-breaking tests.
- Anti-repeat tests.
- Recovery-path tests.
- Repeated-failure tests.
- Session rebalancing tests.
- Backward-compatibility tests with existing v1.8 session lifecycle.

## P3 — Recall Feedback & Recovery Engine ✅

### Goal
Make mistakes educationally useful instead of treating them as terminal binary failures.

### Scope

- Standardize post-answer educational feedback across modes.
- Distinguish:
  - did not know
  - almost knew / near miss when the grader can deterministically establish this
  - wrong
  - correct
- Support progressive retry where educationally appropriate.
- Prevent retry from becoming an unbounded same-answer loop.
- Record whether a later attempt recovered the same attribute during the same session.
- Preserve the meaning of `unknown` as learner feedback rather than turning it into an FSRS rating.
- Keep feedback logic separate from visual rendering.

### Optional but desirable

Where deterministic data exists, provide a compact reason such as:

- expected target
- canonical reading
- accepted vocabulary form
- missing kanji in context

Do not introduce an LLM or remote grader in v1.9.

### Acceptance criteria

- Every supported mode has a defined recovery path.
- Recovery outcomes are distinguishable in session analytics.
- A failed recall can influence the remainder of the current session without rewriting completed history.
- UI rendering consumes a structured feedback object rather than reconstructing educational logic.

### Required tests

- Recovery state machine tests.
- Session feedback tests.
- Browser tests for wrong → retry → recovery.
- Reload/resume tests while a recovery path is active.

## P4 — Learning Evaluation 2.0 ✅

### Goal
Measure whether the adaptive engine is actually better for learning instead of assuming that more adaptation means better learning.

### Metrics

At minimum track deterministic aggregates for:

- attempt accuracy by attribute
- unknown rate
- recovery rate
- repeated-failure rate
- time/order-to-recovery where timestamps are available
- recent-vs-lifetime accuracy
- mastery progression
- retention after successful recall
- mode distribution
- session completion rate
- average recalls per session
- attribute coverage

### Comparisons

Maintain a stable baseline planner for evaluation purposes only.

Compare adaptive vs baseline only when evidence thresholds are met.

### Guardrails

- Evaluation never mutates learner state.
- Evaluation never changes planner parameters automatically.
- Small sample sizes are labeled insufficient rather than overinterpreted.
- Historical outcomes remain interpretable after future grader/planner versions.

### Acceptance criteria

- Evaluation outputs are deterministic from a fixed dataset.
- Baseline comparison is reproducible.
- Evidence sufficiency is explicit.
- Recommendations identify the signal and sample size behind the recommendation.
- Evaluation remains independent of grading implementation.

### Required tests

- Metric fixtures.
- Baseline-vs-adaptive deterministic comparison fixtures.
- Insufficient-evidence tests.
- Versioned-data compatibility tests.

## P5 — Content Quality, Data Integrity & Offline Reliability ✅

### Goal
Reduce the chance that poor content or runtime degradation is mistaken for learner failure.

### Vocabulary quality

- Validate vocabulary examples used by Vocabulary Recall.
- Detect duplicates, empty examples, malformed readings, and unsuitable entries.
- Define deterministic fallback selection.
- Record content provenance/version where needed for reproducibility.

### Context quality

- Validate context sentences before presentation.
- Detect missing/invalid Japanese sentence, translation, or target-kanji placement.
- Keep Tatoeba/API usage as a content provider only.
- Preserve cache and offline fallback behavior.

### Runtime reliability

- Verify every active v1.9 runtime dependency is precached.
- Keep cache versioning aligned with the release.
- Verify offline startup, offline grading, offline session continuation, and recovery.
- Ensure network failure cannot erase a learner outcome.

### Storage integrity

- Preserve bounded history.
- Add deterministic migration paths for any new outcome/model fields.
- Keep canonical storage-key ownership in `v1.5-state.js`.
- Verify no duplicate storage constants reappear in compatibility layers.

### Acceptance criteria

- Invalid content is rejected or safely replaced before it reaches the grader.
- Offline core learning works without external APIs.
- New persisted fields have deterministic defaults/migrations.
- No learner outcome is lost because a network request failed.

### Required tests

- Content-validation fixtures.
- Cache/offline browser tests.
- Storage migration tests.
- Quota/recovery regression tests.
- Network failure tests.

## P6 — Architecture Hardening & v2 Boundary Preparation ✅

### Goal
Finish the architectural cleanup needed so v2 can replace the presentation layer without rewriting the learning engine.

### Scope

Create or strengthen explicit interfaces between:

`education core → planner → session → feedback → state → UI`

### Requirements

- No learning rules embedded in DOM handlers.
- No business logic embedded in CSS or presentation code.
- UI receives structured view-model data from orchestration layers.
- Pure cores remain free of DOM/window/localStorage/network dependencies.
- Compatibility shims are removed when no active consumer depends on them.
- Shared constants live in their canonical owner.
- Session lifecycle remains authoritative for plan persistence and completion history.
- Supabase remains transport-only.

### v2 contract preparation

Define stable data contracts for the future visual layer:

- current session view model
- current exercise view model
- answer feedback view model
- learner skill summary view model
- session summary view model
- adaptive-reason view model

These are contracts, not visual designs. v1.9 must not prescribe the v2 layout.

### Acceptance criteria

- v2 can replace the current presentation layer without importing internal persistence details.
- Pure modules have no browser side effects.
- Architecture tests enforce dependency direction.
- Required public contracts are documented.
- No new v1.9 feature directly hardcodes assumptions about the eventual v2 UI.

### Required tests

- Architecture/dependency tests.
- Contract-shape tests.
- Runtime wiring tests.
- Regression browser smoke tests.

# Explicitly out of scope for v1.9

The following should **not** become v1.9 scope unless required to preserve the learning engine:

- Major visual redesign.
- New navigation paradigm.
- New dashboard design system.
- Theme overhaul.
- Animation-heavy UX work.
- New sixth exercise/recall attribute.
- Replacing FSRS.
- Replacing local-first persistence.
- Introducing an LLM/remote API as the authoritative grader.
- Building a social/gamification system.
- Large-scale content expansion unrelated to recall quality.

These belong primarily to v2 or later.

# Suggested implementation sequence

The recommended execution order is:

`P0 Grading Contract → P1 Learner Model → P2 Adaptive Planner → P3 Recovery → P4 Evaluation → P5 Data/Offline → P6 Architecture Boundary → P7 Release`

Do not implement P2 as a speculative rewrite before P0 and P1 are stable. The planner should consume tested learner-model signals, not invent its own interpretation of raw session history.

Similarly, do not treat P4 as a vanity analytics layer. Evaluation is the evidence gate that determines whether the v1.9 adaptive changes are actually worth carrying into v2.

# v1.9 Definition of Done

v1.9 is complete only when all of the following are true:

- The five learning modes share a stable, versioned outcome contract.
- Grading remains deterministic and educationally conservative.
- Learner state contains meaningful attribute-level and Kanji-level evidence rather than only aggregate accuracy.
- Adaptive planning uses the learner model deterministically and does not replace FSRS.
- Recovery is a first-class learning outcome, not an ad-hoc retry hack.
- Evaluation can compare adaptive behavior against a stable baseline without mutating learner state.
- Vocabulary/Context content failures cannot masquerade as learner errors.
- Core learning remains usable offline.
- Storage migrations and outcome/model versions are deterministic.
- The learning engine is cleanly separable from presentation concerns.
- v2 can replace the visual layer without rewriting the educational core, session lifecycle, persistence contracts, or planner semantics.
- All release gates are green and the repository is clean.

# v2 handoff target

At the end of v1.9, the project should conceptually have this stable stack:

`FSRS card scheduling`

`↓`

`Learner Model 2.0`

`↓`

`Adaptive Planner 3.0`

`↓`

`Session + Recovery + Feedback`

`↓`

`Stable View Models / Contracts`

`↓`

`Current UI (v1) → replaceable by v2 visual UI`

The major v2 effort can therefore focus on presentation, interaction design, information architecture, accessibility, responsive layout, and visual identity rather than reopening the learning-engine foundations.
