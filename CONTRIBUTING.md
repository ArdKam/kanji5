# Contributing to Kanji5

Thanks for contributing.

## Scope and branch discipline

Use a focused branch for each change. Keep PRs narrow enough to review independently. Do not combine unrelated UX, learning-engine, persistence, security, or feature work into a documentation/governance PR.

## Before opening a PR

- Read the relevant roadmap section.
- Check current `main` before claiming work is complete.
- Run relevant tests.
- Update user-facing documentation when behavior changes.
- Update privacy/third-party documentation when data flows or services change.
- Never commit secrets, tokens, private backups, or user data.

## Pull requests

Every PR should state what changed, why, verification performed, and known limitations/release blockers. Use the repository PR template.

## Issues

Use structured issue forms where possible. Do not report security vulnerabilities, credentials, private backups, or account/privacy requests in public issues. A dedicated private privacy/account-request channel is not yet operational.

## Content and provenance

When changing educational data or external content integration, preserve source attribution and provenance metadata. Do not replace authoritative learning-engine behavior with provider output.
